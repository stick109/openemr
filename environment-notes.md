## Windows PowerShell Notes

- For local OpenEMR readiness checks, use HTTP endpoints, Docker health status, or a PowerShell/.NET certificate callback only when HTTPS response content must be inspected.
- 2026-05-01: Symptom: piping literal answers into interactive native commands such as `git add -p` can prepend a UTF-8 BOM to the first response, causing prompts to reject the first answer or consume later answers against the wrong hunk. Likely cause: Windows PowerShell pipeline encoding can emit a BOM for native stdin in this session. Workaround: avoid scripted interactive input for patch staging; prefer `git apply --cached` with explicit patches, or verify the staged diff immediately after any interactive staging. Follow-up: keep selective staging non-interactive when unrelated user edits are present.
- 2026-05-01: Symptom: passing a variable immediately after a native option prefix, such as `mariadb -P$prodPort`, can pass the literal string `$prodPort` and fail with errors like `Unknown suffix '$' used for variable 'port'`. Likely cause: Windows PowerShell does not expand variables embedded directly after arbitrary native option text the way POSIX shells do. Workaround: pass native arguments separately, for example `-P $prodPort`, or use an explicitly quoted single argument such as `"-P$prodPort"`. Follow-up: avoid concatenated native option variables in production database commands.
- 2026-05-01: Symptom: chaining native commands with `&&`, such as `git add ... && git commit ...`, fails with `The token '&&' is not a valid statement separator in this version.` Likely cause: this session is Windows PowerShell rather than PowerShell 7. Workaround: run commands separately or check `$LASTEXITCODE` explicitly between commands. Follow-up: avoid shell-style `&&` chaining in this workspace.
- 2026-05-01: Symptom: `Invoke-WebRequest -SkipHttpErrorCheck` fails in Windows PowerShell with `A parameter cannot be found that matches parameter name 'SkipHttpErrorCheck'`. Likely cause: that switch is available in newer PowerShell versions, not this Windows PowerShell session. Workaround: use `try`/`catch` around `Invoke-WebRequest` and read `$_.Exception.Response`, or run a newer `pwsh` if installed.
